# Loan Application System: API Documentation

Version 0.1 (draft for the college demo). Backend: FastAPI. Database and auth: Supabase. Model: XGBoost with SHAP explanations.

This document describes every endpoint in the planned API. Items marked **\[Assumption\]** are choices I made where your project context did not specify a detail; change them if you disagree.

## 1. Overview

| Item | Value |
| --- | --- |
| Base URL (local) | http://localhost:8000 |
| Format | JSON request and response bodies, UTF-8 |
| Auth | Bearer token in the Authorization header |
| Interactive docs | /docs (Swagger UI) and /redoc, generated by FastAPI |
| Two roles | customer (OTP-verified session) and banker (Supabase Auth user with role = banker) |

### Key principles

- The model only recommends. A banker makes every final decision.
- Customers never receive risk\_score, risk\_label or top\_factors in any response.
- The Supabase service role key stays on the backend. The frontend only talks to this API.
- Every customer endpoint derives the customer from the session token, never from an ID in the request body or URL.

## 2. Authentication

### Customer session

1. POST /auth/verify with account number, registered mobile and date of birth. The backend checks them together and sends an OTP (mock for the demo).
2. POST /auth/otp with the challenge ID and the OTP. The backend returns a session token.
3. Send the token as `Authorization: Bearer <token>` on all customer endpoints.

**\[Assumption\]** The customer session token is a short-lived signed JWT issued by the backend itself (not a Supabase Auth session), with claims `sub` (customer\_id), `role` = customer and `exp` (30 minutes).

### Banker session

Bankers sign in through POST /banker/login, which wraps Supabase Auth email and password sign-in. The backend rejects any user whose user metadata does not have role = banker. The returned token is the Supabase access token, verified on each banker request.

### Access matrix

| Endpoint group | Customer token | Banker token | No token |
| --- | --- | --- | --- |
| /auth/\* | n/a | n/a | allowed |
| /customer/*, /applications/* | allowed | 403 | 401 |
| /banker/login | n/a | n/a | allowed |
| /banker/\* (others) | 403 | allowed | 401 |

## 3. Conventions

### Error format

All errors use one shape:

```json
{"error": {"code": "VALIDATION_ERROR", "message": "tenure_months must be between 6 and 84", "details": [{"field": "tenure_months", "issue": "out_of_range"}]}}
```

`details` is optional.

### Status codes

| Code | Meaning | Error code |
| --- | --- | --- |
| 200 | OK | n/a |
| 201 | Created | n/a |
| 400 | Malformed request | BAD\_REQUEST |
| 401 | Missing, invalid or expired token | UNAUTHORIZED |
| 403 | Wrong role | FORBIDDEN |
| 404 | Resource not found, or not owned by the caller | NOT\_FOUND |
| 409 | Conflict, such as a decision already recorded | CONFLICT |
| 422 | Validation failure | VALIDATION\_ERROR |
| 429 | Too many attempts | RATE\_LIMITED |
| 500 | Unexpected server error | INTERNAL\_ERROR |

### Data types

- Dates: ISO 8601, `YYYY-MM-DD`. Timestamps: ISO 8601 UTC.
- Money: numbers in INR, no currency symbol. **\[Assumption\]** Currency is INR throughout.
- Application number: format `LN-YYYY-NNNNNN`, for example `LN-2026-000042`.

### Enumerations

| Name | Values |
| --- | --- |
| status | submitted, under\_review, approved, rejected, more\_info |
| risk\_label | Normal, Risky (0 = Normal, 1 = Risky in the model target) |
| decision | approved, rejected, more\_info |

## 4. Customer endpoints

### 4.1 POST /auth/verify

Starts verification. Checks account number, registered mobile and date of birth together, then sends an OTP.

**Request body**

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| account\_number | string | yes | The customer's bank account number |
| mobile | string | yes | Registered mobile number |
| dob | string | yes | `YYYY-MM-DD` |

**Success: 200**

| Field | Type | Notes |
| --- | --- | --- |
| challenge\_id | string | Opaque ID, sent back with the OTP |
| expires\_in | integer | Seconds until the OTP expires (for example 300) |
| message | string | "OTP sent to the registered mobile number" |

**Failure: 401**

On any mismatch the response is the same generic error and never reveals which field was wrong: `{"error": {"code": "VERIFICATION_FAILED", "message": "We could not verify these details."}}`

The response time and body must be identical whether the account exists or not.

**Notes**

- Mock OTP for the demo: the OTP is a fixed value from config (for example `123456`) or is logged to the server console. It is never returned in the API response.
- **\[Assumption\]** Rate limit: 5 verify attempts per account per 15 minutes, then 429.

### 4.2 POST /auth/otp

Validates the OTP and issues a session token.

**Request body**

| Field | Type | Required |
| --- | --- | --- |
| challenge\_id | string | yes |
| otp | string (6 digits) | yes |

**Success: 200**

| Field | Type | Notes |
| --- | --- | --- |
| access\_token | string | Bearer token for customer endpoints |
| token\_type | string | "bearer" |
| expires\_in | integer | Seconds |

**Failures**

| Code | When |
| --- | --- |
| 401 INVALID\_OTP | Wrong or expired OTP |
| 429 RATE\_LIMITED | **\[Assumption\]** 3 wrong attempts invalidate the challenge, and the customer must restart from /auth/verify |

### 4.3 GET /customer/profile

Returns the customer's on-file details for the read-only confirmation screen. Requires a customer token.

**Success: 200**

| Group | Fields |
| --- | --- |
| identity | full\_name, dob, mobile (masked), account\_number (masked) |
| personal | marital\_status, education, family\_size, residence\_type, owns\_property |
| employment | occupation, income\_type, employer\_name, employment\_start\_date |
| financial | annual\_income |

**Notes**

- Sourced from the customer\_features view and related tables.
- **\[Assumption\]** The profile does not include ext\_score\_1, ext\_score\_2, ext\_score\_3, enquiries\_last\_year or any other credit bureau data. This keeps risk-related inputs hidden from the customer.
- Gender is not a model input and is not needed here.

### 4.4 POST /applications

Submits a new loan application. This is the core endpoint. Requires a customer token.

**Request body**

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| loan\_amount | number | yes | Greater than 0. **\[Assumption\]** Between 10,000 and 5,000,000 (configurable) |
| tenure\_months | integer | yes | **\[Assumption\]** Between 6 and 84 (configurable) |
| purpose | string | yes | Short text or a fixed list such as home, education, vehicle, personal, business |
| declared\_income | number | no | Customer-declared annual income |
| consent | boolean | yes | Must be true, otherwise 422 |

**Processing steps (server side)**

1. Identify the customer from the token and load the row from customer\_features.
2. Compute monthly\_installment with the EMI formula and the fixed interest rate from config.
3. Compute credit\_to\_income = loan\_amount / annual\_income and installment\_to\_income = monthly\_installment / annual\_income. Annual income is used, not monthly.
4. Fill missing ext\_score\_N values with the medians (0.505994, 0.566198, 0.535276) and set the matching ext\_score\_N\_missing flag to 1, otherwise 0.
5. Ordinal-encode the five categorical columns with the saved encoder, in the training column order. Unknown values become -1.
6. Build the 21-feature row in exact training order and run the model.
7. Compute SHAP values and keep the top factors.
8. Apply the threshold from config to set risk\_label.
9. Insert the loan\_applications row with status = submitted, the risk output and the generated application number.

**Success: 201**

| Field | Type | Notes |
| --- | --- | --- |
| application\_no | string | For example LN-2026-000042 |
| status | string | "submitted" |
| submitted\_at | string | UTC timestamp |

The response contains no risk information.

**Failures**

| Code | When |
| --- | --- |
| 422 | Validation failed or consent is not true |
| 409 | **\[Assumption\]** The customer already has an application in submitted, under\_review or more\_info status |
| 500 | Model or database failure (the error message to the customer stays generic, details go to the server log) |

**Decision for you: declared\_income.** The model was trained on on-file annual income. **\[Assumption\]** declared\_income is stored on the application for the banker to see, but the model features and both ratios still use the on-file annual\_income. If you want the model to use declared income, say so, because that changes the feature pipeline.

### 4.5 GET /applications/{application\_no}

Returns the status of one of the customer's own applications. Requires a customer token.

**Success: 200**

| Field | Type |
| --- | --- |
| application\_no | string |
| status | string |
| loan\_amount | number |
| tenure\_months | integer |
| purpose | string |
| submitted\_at | string |
| monthly\_installment | number |

`monthly_installment` is the quoted EMI, not a risk field, so it is safe to show.

**Failures**

- 404 if the application does not exist or belongs to another customer (the same response for both, so existence is not leaked).

**Never returned:** risk\_score, risk\_label, top\_factors, remarks, decided\_by. **\[Assumption\]** For `more_info`, the screen shows a fixed message such as "The bank needs more information. Please contact your branch." Banker remarks are not exposed.

### 5.3 GET /banker/applications/{id}

Full detail for one application. `{id}` is the internal ID of the loan\_applications row (returned by the list endpoint). **\[Assumption\]** Using the internal ID keeps application\_no purely a customer-facing reference.

**Success: 200**

| Section | Contents |
| --- | --- |
| application | id, application\_no, status, loan\_amount, tenure\_months, purpose, declared\_income, monthly\_installment, interest\_rate\_used, submitted\_at |
| customer | name, dob, age\_years, mobile, marital\_status, education, family\_size, residence\_type, occupation, income\_type, annual\_income, employed\_years |
| risk | risk\_score, risk\_label, threshold\_used, top\_factors |
| features | The 21 model inputs as submitted to the model, as an object in training order |
| display\_only | existing\_loans, credit\_cards, accounts, credit\_profiles, assets (not model inputs) |
| decision | decision, remarks, decided\_by, decided\_at (all null until decided) |

**top\_factors** is an array, ordered by absolute impact, of objects with these fields:

| Field | Type | Notes |
| --- | --- | --- |
| feature | string | One of the 21 feature names |
| label | string | Human-readable label, for example "External score 2" |
| value | number or string | The feature value for this application (decoded for categories) |
| shap\_value | number | Signed contribution to the risk score |
| direction | string | "increases\_risk" or "decreases\_risk" |

Show the top 5 factors by default (configurable).

**Status side effect \[Assumption\]:** The first time a banker opens a submitted application, its status moves to under\_review. If you prefer a read-only GET, remove this and add an explicit claim endpoint.

**Failures:** 404 if the ID does not exist.

### 5.4 POST /banker/applications/{id}/decision

Records the final decision.

**Request body**

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| decision | string | yes | approved, rejected or more\_info |
| remarks | string | conditional | Required for rejected and more\_info, optional for approved. Maximum 1000 characters |

**Success: 200**

Returns the updated decision block: status, decision, remarks, decided\_by, decided\_at.

**Effects**

- Sets loan\_applications.status to the decision value, and sets decision, remarks and decided\_by (the banker's Supabase user ID).
- The risk fields are never modified by this call.

**Failures**

| Code | When |
| --- | --- |
| 404 | Application not found |
| 409 | **\[Assumption\]** The application is already approved or rejected. A more\_info application can still receive a new decision |
| 422 | Invalid decision value, or remarks missing when required |

**Note:** your schema lists decision, remarks and decided\_by but no decided\_at column. If you want a decision timestamp, add `decided_at` to loan\_applications. Otherwise drop it from this response.

## 7. Status lifecycle

| From | To | Triggered by |
| --- | --- | --- |
| (none) | submitted | POST /applications |
| submitted | under\_review | Banker opens the detail (see 5.3) |
| submitted or under\_review | approved, rejected, more\_info | POST /banker/applications/{id}/decision |
| more\_info | approved, rejected, more\_info | Another banker decision |

## 9. Reference: model input and EMI

### EMI formula

With r = annual\_rate / 12 / 100 and n = tenure\_months:

EMI = P \* r \* (1 + r)^n / ((1 + r)^n - 1)

where P is the loan amount. If r = 0, EMI = P / n.

### The 21 features, in exact order

| # | Feature | Source |
| --- | --- | --- |
| 1 | owns\_property | customer\_features view |
| 2 | annual\_income | customer\_features view |
| 3 | credit\_amount | Request loan\_amount |
| 4 | monthly\_installment | Computed EMI |
| 5 | income\_type | View, ordinal-encoded |
| 6 | education | View, ordinal-encoded |
| 7 | marital\_status | View, ordinal-encoded |
| 8 | residence\_type | View, ordinal-encoded |
| 9 | occupation | View, ordinal-encoded |
| 10 | family\_size | customer\_features view |
| 11 | ext\_score\_1 | View, median-filled if null |
| 12 | ext\_score\_2 | View, median-filled if null |
| 13 | ext\_score\_3 | View, median-filled if null |
| 14 | enquiries\_last\_year | customer\_features view |
| 15 | age\_years | (today - dob) in years |
| 16 | employed\_years | (today - employment start) in years, 0 if no start date |
| 17 | credit\_to\_income | credit\_amount / annual\_income |
| 18 | installment\_to\_income | monthly\_installment / annual\_income |
| 19 | ext\_score\_1\_missing | 1 if ext\_score\_1 was null |
| 20 | ext\_score\_2\_missing | 1 if ext\_score\_2 was null |
| 21 | ext\_score\_3\_missing | 1 if ext\_score\_3 was null |

The feature row must match training exactly in order, units and formulas, or predictions will be silently wrong.

## 10. Security checklist

- Generic error on verification failure, with the same timing for a missing account.
- Customer identity comes only from the token. Never trust an ID from the client.
- Risk fields are stripped from every customer response. Use separate Pydantic response models for customer and banker so a field cannot leak by accident.
- The service role key never reaches the frontend or the repository (keep .env in .gitignore).
- Banker endpoints verify the token and role = banker on every request.
- Pin scikit-learn to 1.6.1, because the encoder was pickled with that version.
- Restrict CORS to the frontend origin.
